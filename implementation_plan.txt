Stage 0 — Foundations

Get the skeleton running before any AI touches it.

Repo scaffold matching §23 structure (frontend/, backend/, ai/, workers/)
FastAPI app + MongoDB connection + basic health check route
Next.js app with Tailwind/shadcn wired up
Docker Compose: Mongo, Redis, MinIO (skip OpenSearch/Qdrant for now — add in Stage 4)
.env handling per §25
Phone OTP auth (or mocked OTP for dev) + JWT issuing

Exit criteria: you can register a user and hit a protected route.

Stage 1 — Seller Core (MVP, no AI)

Prove the basic seller → product → catalogue → publish loop with manual input, deterministic pricing only.

Seller profile + workspace info CRUD
Product creation form (manual fields: material, cost, days, workers, capacity)
Deterministic Pricing Engine (§11) as a standalone Python module — pure math, build and unit-test it first since everything downstream depends on it
Basic catalogue record → publish → list products (simple grid, no search yet)
Image upload to MinIO/S3 (no AI quality check yet, just accept + store)

Exit criteria: a seller can manually create a listing and see a computed price recommendation.

Stage 2 — Buyer Core (MVP, no AI)
Buyer browse/list view of published products
Manual filters (price, category) — skip semantic search for now
Order creation (simple, single-seller, no negotiation yet)
Order status tracking (basic state machine: placed → in_production → delivered)

Exit criteria: end-to-end seller-lists → buyer-orders flow works without any AI.

This gives you a demoable product early — important checkpoint before AI complexity hits.

Stage 3 — AI Layer, Phase 1 (Voice + Catalogue Agent)

Now replace manual seller input with the voice-first flow.

Whisper (or hosted ASR) for speech-to-text
Multilingual Voice Agent: extract structured JSON (material_cost, days, workers, capacity) per the §10 schema — start with one LLM call + strict JSON schema validation, add retry-on-malformed-output
Catalogue Agent: title/description/tags generation from extracted data — keep it editable, never auto-publish without seller review
Confidence policy (§19): low-confidence fields prompt the seller instead of auto-filling

Exit criteria: seller can speak a product description and get a pre-filled, editable catalogue draft.

Stage 4 — AI Layer, Phase 2 (Vision + Photography Assistant)
Lightweight CV checks (OpenCV: brightness/blur/framing) for real-time capture feedback — not an LLM call per frame
Post-capture: heavier vision-language model pass for product attribute extraction (optional, can reuse catalogue agent)
Live camera capture flow enforced (no gallery upload) for the 3–5 mandatory images from §12

Exit criteria: seller gets real-time "too dark / move closer" feedback while capturing, and images get quality-scored before submission.

Stage 5 — Search & Matching

This is where OpenSearch + Qdrant actually justify their existence — add them now, not in Stage 0.

OpenSearch for structured/keyword search
Qdrant for embedding-based semantic search on product descriptions
Buyer Requirement Agent: NL query → structured filters (§10 example)
Matching Engine: combine semantic candidates + price/capacity/deadline filters into ranked results

Exit criteria: buyer can type a natural-language requirement and get ranked, relevant sellers back.

Stage 6 — Negotiation & Multi-Artisan Orders
Negotiation Agent (LLM + price-floor guard) — hard-enforce that it can never accept below seller's floor (§19 principle: AI proposes, rules validate)
WebSocket chat for buyer↔seller
Multi-artisan order splitting logic (§14) — greedy capacity allocation is enough to start; don't over-engineer the optimizer

Exit criteria: a buyer can negotiate on price and place a bulk order split across multiple sellers.

Stage 7 — Trust & Fraud
Perceptual hashing for duplicate-image detection
Simple rule-based risk score (weighted signals: OTP verified, image integrity, location consistency) — save ML-based scoring for §29 future work
Risk tiers → auto-verify / additional-verification / manual review queue

Exit criteria: fake/duplicate submissions get flagged and routed to review instead of silently published.

Stage 8 — Reliability, Offline Handling, Monitoring
Async queue (Celery + Redis) for all AI calls — API responds immediately, AI result lands later
Client-side draft persistence for network failures (§21)
Prometheus + Grafana dashboards, Sentry error tracking
Graceful AI-outage messaging (§21 example)

Exit criteria: killing the AI worker or losing network mid-flow doesn't lose seller data.

Stage 9 — Polish & Deployment
Docker Compose → single-node deployment (Kubernetes only if you actually need multi-node scale — skip for hackathon/demo)
CI/CD via GitHub Actions (lint + test on push)
Seed demo data (a few sellers, products, one bulk-order scenario) so the demo doesn't rely on live AI calls under time pressure
